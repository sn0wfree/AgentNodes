> **本方案先解决一个前提问题：90% 的分母是什么。** 不同定义下所需
> 工作量差 3 倍以上（见 §1），必须先定范围再动手。

## 2. 三个可选目标（必须选一个）

### 选项 1：活跃核心 90%（**推荐**）

范围 = A + B + C，排除 `_archived/`、CLI 交互向导、外部数据加载器。

- 当前 ~80.9%（23,242 stmts / 4,436 missed）
- **到 90% 需补 ~2,100 条覆盖**
- 工期估计：**3-5 天**（集中在 B 研究域）
- 价值：覆盖所有业务逻辑与平台契约；排除的是「测试投入产出比低」的部分

### 选项 2：全库 90%（含归档与外部依赖）

- 当前 68%
- 到 90% 需补 ~11,500 条
- 工期估计：**3-4 周**
- 代价：要给 1,485 条死代码写测试（或删掉），要给 akshare/ifind/tushare 加载器造大量 mock，要给 TUI 交互写模拟
- **不推荐**：这会让我们为「已经决定不用的代码」付维护成本

### 选项 3：全库 90%，同时删除 `_archived/` 并排除外部依赖

- 分母从 53,530 降到 ~40,000（删 1,485 死码 + 排除数据加载器的网络分支）
- 到 90% 需补 ~7,000 条
- 工期：**2 周**
- 折中方案，但要先做一次「删除归档代码」的决策（涉及 13 个文件）

## 3. 推荐执行路径（选项 1）

### 3.1 第一步：立规矩（0.5d）

| 事项 | 内容 |
|---|---|
| `.coveragerc` | `omit` 归档目录、`__main__`、`conftest`；`branch = True`（分支覆盖比行覆盖更有意义） |
| CI 门禁 | `--cov-fail-under=90`，但**只对 A+B+C 生效**（用 `--cov=strategy_research/core/...` 分范围） |
| 报告脚本 | `scripts/cov_gate.py`：按 A/B/C 三档分别断言，避免一刀切的假达标 |

### 3.2 第二步：按缺口排序补测（3-4d）

按未覆盖语句数排序，**优先补业务价值高的**：

| 优先 | 模块 | 未覆盖 | 补什么 |
|---|---|---:|---|
| 1 | `core/study/scheduler.py` | 142 | 并发/取消/恢复路径（已有部分） |
| 2 | `core/study/runner.py` | 128 | 生命周期分支（暂停/恢复/预算耗尽/监控阶段） |
| 3 | `core/goal/workflow.py` | 123 | goal 状态机分支 |
| 4 | `core/study/dag_planner.py` | 58 | 计划生成分支 |
| 5 | `core/agent/loop.py` | 63 | 已有 88%，补边界 |
| 6 | `core/swarm/runtime.py` | 102 | 层屏障/失败隔离 |
| 7 | `core/llm/openai_client.py` | 112 | 重试/超时/流式分支（**mock 传输层**） |

**方法论**：不为覆盖率写测试。每补一个模块，先看未覆盖行是**真分支**还是
**防御性 except**——后者用 `# pragma: no cover` 标注（这是行业标准做法，
不是作弊：无法触发的 except 写测试只是自欺）。

### 3.3 第三步：明确豁免（随第一步一起）

`.coveragerc` 的 `exclude_lines`：

```
pragma: no cover
raise NotImplementedError
if TYPE_CHECKING:
if __name__ == .__main__.:
```

象征性豁免（不进 90% 分母）：`core/data_source/*_loader.py` 的网络分支、
`cli/onboard.py` 的交互问答、`cli/tui/` 的渲染布局。

## 4. 必须诚实说明的三件事

1. **当前 68% 里，有 1,485 条是 0% 的死代码在拖分母**。如果不排除，
   「全库 90%」要么意味着给死代码写测试，要么意味着删掉它们——这是
   另一个决策，不是测试工作。
2. **平台内核已 91.1%**。本轮 R1–B3 重构没有降低质量，反而因为
   每刀必测而高于全库平均。
3. **覆盖率是手段不是目的**。100% 覆盖的代码可以有 bug（未测的断言、
   错的 mock）；而 `except Exception: pass` 这类行覆盖了也没意义。
   90% 是合理目标，但「补哪 2100 条」比「到 90%」重要。

## 5. 建议的下一步

先确认选哪个选项。选 1 的话，我会：
1. 建 `.coveragerc` + 分档门禁脚本 + CI 接线（0.5d）
2. 按 §3.2 顺序逐模块补，每模块补完立即跑该模块覆盖率验证（3-4d）
3. 每轮结束跑全量，报告「A/B/C 三档实际覆盖率」+ 新增测试数

选 2 或 3 的话，需要先决策 `_archived/` 的处置（删除 or 保留并排除）。
