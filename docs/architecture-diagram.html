层职责与模块化原则

层体量职责边界模块化原则
L1 interfaces120 文件
30.3k 行		唯一出口：把外部请求包成 WorkRequest，订阅事件流回给调用方。不含业务判断。按渠道分（api / cli / mcp）+ 一个组装根。组装根是唯一允许知道 apps 具体实现的 L1 模块。
L2 apps625 文件
66.1k 行		研究 IP 的全部所在。方法论、因子、回测、进化都在这层。按业务能力分四个功能域；域间不互相 import，协作走 L3 的端口或事件流。
L3 kernel175 文件
36.7k 行		业务无关的平台机制：控制、执行、能力供给。不认识研究语义。按机制职责分三个子带（控制面 / 执行面 / 能力面）；同层自由互调，只向下依赖。
L4 foundation64 文件
10.9k 行		零业务知识的基础设施。被上面三层共同依赖。按技术能力分（llm / storage / utils / observability / web）。晋升门槛＝去掉 run/session 语义可独立成库。

模块间协作：三条通道

通道路径为什么必须这样
下行调用上层直接 import 下层的公开接口（L1→L2→L3→L4）依赖方向单一，静态可验证（AST 门禁）
端口回调kernel 不 import apps，改为 CapabilityRegistry.resolve(kind) 拿到实现；apps 在 import 时主动注册这是 L3→L2 从 46 降到 0 的唯一手段——把依赖方向倒过来，而不是把 import 藏进函数
事件流一切状态变更写 event_log；跨域观察靠订阅，不靠直接调用事件流是唯一事实源，保证崩溃可恢复、状态可 replay
