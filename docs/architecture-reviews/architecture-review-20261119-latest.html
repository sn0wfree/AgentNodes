问题。 B2.2 设计 §2 指定 L3 `kernel/agent/tools/isolation.py`，已实现代码位于 L2 `apps/chat/isolation.py`。后续 kernel 工具调用不得依赖 apps。

建议。 默认让通用 worker/平台机制归 kernel；若保留 apps adapter，则由高层注入并以真实调用链测试，不能添加上行导入。

收益。 locality：平台机制与执行者共处合法 seam；leverage：经准入的工具复用一致的隔离行为；测试对准真实调用路径。

当前状态：3a/3b/3c 已提交，未见生产接线。建议在 3d 或 B2.3 扩大前补层级归属裁决，避免后续接线后再搬迁。

问题。 过去的 eager prune 尝试把已知终态 approve 从 409 变成 404。两个 registry 不是重复所有者，不应合并。

建议。 先定保留期限/触发点以及过期后如何识别已知终态；再单独增加清理策略和测试。

收益。 lifecycle 规则集中，status/approve 行为可测试；保留客户端依赖的错误语义。

默认：未裁决前不接自动 prune；暂时保留已知终态记录，保证 known-terminal 与 unknown 的区别。

需要讨论/批准的事项（推荐值不是批准）

  1. 1. Isolation seam 所有权。 设计写 L3 `kernel/agent/tools/isolation.py`，实现位于 L2 `apps/chat`；推荐通用机制归 kernel，或提供可验证的高层注入，禁止上行依赖。
  2. 2. 是否批准 B2.2 3d。 Windows 必过，POSIX 只做有理由的 skip/unsupported；生产支持前需跨平台验证。
  3. 3. 隔离执行后续批次。 B2.3、B2.4、B2.5 各自 R-014、独立验收；首试点仅临时目录 file_write，shell 延期。
  4. 4. M13 终态期限。 未决定前不做自动 prune；保留已知终态以稳定 approve 409 与未知 404 的差异。
  5. 5. RSI 归属。 推荐新建 `apps/evolution`，按策略、run_once、wiring 分批，不并入 `apps/goal`。
  6. 6. 批 3c 七项归拢。 M3/M5/M7/M8 可分别派；M6/M9 与 M3/M11 需错开共享文件热区。
  7. 7. 兼容出口删除。 3a.4 延至下一版本另批；Legacy Chat 至少一个完整正式版本周期后再审；不得预先删除。
  8. 8. seq_generator 退役。 推荐独立公告和 R-014 批次，四类触点一并同步，不与 Chat 删除合并。

Top recommendation

先裁决隔离 seam 所有权，再批准 B2.2 3d

3a/3b/3c 已完成且未接生产；下一执行阶段是平台矩阵。继续前先协调设计所指 L3 与实现所在 L2， 避免平台测试完成后才发现生产调用只能通过非法上行依赖。M13 终态策略可作为不冲突的独立小批讨论； RSI 与七项应用归拢可先写各自实施清单，不必等待隔离链完成。
