Problem. B2.2 方案目标写 `kernel/agent/tools/isolation.py`，实际提交新增 `apps/chat/isolation.py`；测试也只从 apps/chat import。通用 tool execution 属于 L3，之后 BaseTool 不能合法依赖 L2。

Solution. 在 B2.2 3b 前用短 R-014 修订确认 owner：若这是通用隔离执行 seam，归 kernel；若坚持 apps owner，则必须明确由更高层注入 adapter、kernel 不直接 import apps，并证明真实调用链可运行。

Wins. locality：平台机制与调用者同层；leverage：所有工具共用一个合法 seam；层级门禁继续约束依赖方向。

需要先决定的不是代码形状，而是所有权。 本轮模块零生产接线，因此现在校准成本最低；不要先加 IPC，再在 B2.4 被 L3→L2 约束迫使搬迁。
验收。 方案、实现和架构图位置一致；有一条合法的 kernel→隔离 seam 调用路径（或有明确注入 adapter 的测试）；POSIX 禁启用、Windows E1/E5 行为保持。

Problem. `WorkflowRunRegistry.prune()` 没有生产调用；终态 runner 会留在 `_runs`。直接 prune 已使 approve 对终态对象由 409 变 404。

Solution. 不合并两个互补 registry；先裁决终态信息保留多久及 404/409 契约，再设计有限 TTL / 持久记录查询策略。

Wins. locality：终态与生命周期规则可定位；leverage：status/approve 共用清晰语义；测试覆盖成功、过期与重复操作。

状态。 M13 审查已判两个 registry 互补。该候选只处理 kernel registry 的终态滞留，需独立 R-014；目前不预设 TTL 时长或把存在性判断改到持久层。

建议下一步执行计划

  1. 先修订 B2.2 3a 归属说明。 写一个小范围 R-014：解释为何代码从目标 kernel 路径落在 apps/chat，确认最终 owner 和合法调用路径；只涉及模块归属/设计同步，不接生产。
  2. 若归 kernel：单独迁移 seam，再做 3b。 保持 Windows adapter 延迟导入、POSIX 显式禁用和 E1/E5 行为；测试验证层级方向和平台语义。若选择 L1 注入，则测试必须真实穿过组合根到 kernel caller，不能只测注入 helper。
  3. 随后批准并执行 3b。 添加 JSON Lines IPC、审批请求代理、结果/错误协议与 `actual_state` 对齐；保留零生产接线。验收 E2/E3、异常/退出/取消清理、超时结果拒收。
  4. 独立处理 M13 终态保留。 先定 409/404 对用户的契约和保留期限，再以行为测试实现；不要合并 router goal registry 与 kernel definition registry。
  5. 再推进 3c / 3d。 仅用临时工作区 `WriteFileTool` 做脚本级试点，shell 不纳入；Windows 真机验证，POSIX 在跨平台生产启用前验证。3d 后再单独批准 B2.3；B2.5 前不接生产路径。
  6. 删除按原裁决等待。 legacy chat/3a.4 至少经历一个完整正式版本周期并独立审批；seq_generator 单独退役批。OptionsPricingTool 与 hooks 保留。

Top recommendation

B2.2 继续前，先对齐隔离执行 seam 的层级所有权

这是尚未接生产、又会影响后续 L3 tool runtime 接线的早期架构选择。方案写 kernel，代码落 apps/chat；直接进入 IPC 子批会扩大实现后再搬迁的风险。先用一份小 R-014 修订决定 owner 与调用路径，再继续 3b。M13 终态保留则是另一项独立的状态语义任务。
