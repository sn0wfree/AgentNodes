## 三、本轮新增的两条门禁教训（建议固化为工具）

### 3.1 `check_dangling_imports` 的盲区：只校验模块存在，不校验名字

本轮真实的 `get_store` 悬空（`loop.py:488`）它没抓到，因为
`foundation.storage` 是**目录**、模块存在，但 `get_store` 不在其中。

预演结果：全仓 11,124 条 import 做运行时 `getattr` 校验，**13 处取不到名字**，
分类如下：

| 类别 | 数量 | 处置 |
|---|---|---|
| 真 bug | **1** | `loop.py:488 get_store` —— 已修（改为读 L4 注入槽） |
| `TYPE_CHECKING` 内引用错模块 | **2** | `study/{bootstrap,runner}` 的 `StudyGraph` —— 已修（改指 `study/graph.py`） |
| `TYPE_CHECKING` / `try-except` 保护内且名字正确 | 4 | 合法 |
| 负向断言（故意 `pytest.raises(ImportError)`） | 4 | 合法 |
| 过时测试引用 | 2 | `test_tools_capability.py` 已修；`test_plan_build_mode.py` 待人（见 §1.1） |

**建议**：把运行时 `getattr` 校验固化为 `scripts/arch/check_import_names.py`，
并内置上述豁免机制（TYPE_CHECKING/try 块、`# import-name: ok` 行标记）。

> ⚠ 注意：静态推断会报 150 处误报（TYPE_CHECKING、条件定义、动态赋值抓不全），
> **必须走 import + getattr**，不能纯 AST。

### 3.2 判环的终审标准不是图算法

评审 §2.5 已记录：包级 SCC 会产生假环，`TYPE_CHECKING` 边不算运行时依赖，
`from . import X` 的 X 可能是子模块或 `__init__` 名字。
**唯一可信的终审是「该导入顺序是否真的抛 ImportError」**（子进程矩阵）。

建议固化为 `scripts/arch/check_import_cycles.py`：
- 三分类 import（eager / typing / lazy）
- 模块级 SCC（仅 eager）
- 对每个判出的环跑子进程导入矩阵反向验证
