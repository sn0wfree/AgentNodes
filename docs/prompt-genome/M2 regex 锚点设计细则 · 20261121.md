# M2 · Regex 锚点设计细则（script→regex 通道的行为锚点）

> **问题**：script 通道查**工件状态**（代码里有没有 `os.environ`——batch_gate 已在做），regex 通道查**会话行为轨迹**（agent 在会话中实际做了什么）。「逐规则怎么设计行为锚点」就是本细则。
> **上游**：[`rule-genome-design-20261117.md`](rule-genome-design-20261117.md) §3（rule_check entry）· [`可行性研究`](可行性研究 · 困难与证伪点 · 20261120.md)（D2/D6 量具与对抗）· [`触发场景库`](触发场景库 · lessons 转化 · 20261120.md)（R-019 注入法）。
> **状态**：设计稿（2026-11-21 · 未实施）。试点 3 条的具体锚点为**待校准草案**。

---

## 0. 一句话

**锚点 = 前件（触发模式）+ 后件（合规/违规模式）的可机检对**——前件匹配才算这条规则被「触发」，后件决定 verdict；没有前件的纯后件检查会把「没触发」误判成「不确定」，这是锚点设计的头号错误。

## 1. 通道边界：什么该走 regex

| 判据 | 走 script（工件检查） | 走 regex（行为检查） |
|---|---|---|
| 违规证据存在于**落盘产物**（代码/配置/commit） | ✅ | — |
| 违规证据只存在于**会话轨迹**（tool_call 序列/中间产出） | — | ✅ |
| 需要语义理解才能判定 | —（留 judge/人工） | —（超出 regex 能力） |

regex 通道的**定位是抽样观测，不是全量执法**：锚点覆盖不了绕过路径（MCP/其它工具），对抗者知道锚点后会换措辞（表演遵守，D6）——所以 regex 结论用于表达谱统计与试点，不作为唯一阻断依据（阻断仍靠 script 门禁）。

## 2. 锚点四类型

| 类型 | 前件（触发模式） | 后件 | 例 |
|---|---|---|---|
| **tool_call 锚** | tool 名 + 参数模式 | 参数/结果模式 | Bash command 匹配 `git commit` → 检查 message 语言 |
| **text 产出锚** | 产出类型标记 | 文本模式 | agent 输出的 commit message / 回复文本 |
| **序列锚** | 事件 A 出现 | 窗口内事件 B 必现 | `rm ` 出现 → 前 N iter 内必有该目标的 `ls` |
| **否定锚** | 任何 Edit/new_string | **不该出现**的模式 | `os.environ.get("AGENTNODES_` 出现 → violated |

**verdict 映射（四态，不是三态）**：

| 前件 | 后件 | verdict |
|---|---|---|
| 匹配 | 合规模式匹配 | `complied` |
| 匹配 | 违规模式匹配 | `violated` |
| 匹配 | 两者都模糊 | `uncertain`（一等状态） |
| 不匹配 | — | **未触发——不落 rule_check**（只记表达谱的 transcribed 统计） |

★ 「未触发 ≠ uncertain」是锚点协议的关键区分：把未触发记成 uncertain 会污染遵守率统计（分母错）。

## 3. 锚点规格 schema

```jsonc
{
  "rule_id": "an:R-002",
  "anchor_id": "anchor.R-002.env-edit-01",
  "type": "negative",                       // tool_call | text | sequence | negative
  "trigger": { "tool": "Edit", "pattern": "os\\.environ\\.get\\([\"']AGENTNODES_" },
  "compliance": null,                        // 否定锚无合规后件
  "violation": null,                         // 前件即违规证据 → verdict=violated
  "scope": { "iter_window": null, "tools": ["Edit", "Write"] },
  "calibration": {                           // R-019 注入法：量具自检
    "positive_samples": ["os.environ.get('AGENTNODES_BUDGET')"],   // 必须红
    "negative_samples": ["settings.get_float('AGENTNODES_…')"],    // 必须不红
    "hit_cap": 500                           // 命中量上限（GRL C8a 教训：防全集命中）
  },
  "recorded_by": "kernel/regex_hook"
}
```

## 4. 校准协议（借 R-019 注入法 · 仓内已有实践）

每个锚点上线路径 = **注入法校准**（R-019：「门禁看 0 违规不够，要看注入违规会不会红」）：
1. 构造 **positive 样本**（已知违规形态）→ 锚点必须报 `violated`，否则锚点坏；
2. 构造 **negative 样本**（已知合规形态）→ 锚点必须不报，否则查准失败（误伤）；
3. **注入点避开豁免**（R-019 教训：测的是检测逻辑不是豁免逻辑）；
4. **上限检查**：单会话单锚点命中 > hit_cap → 判锚点失控（False positive 洪水），告警而非记账；
5. 校准样本集**进 git**（每锚点一组样本文件），量具改动 CI 重跑（可行性 C12）。

## 5. M2 试点的三条锚点（候选理由：历史数据即校准集）

### 试点 1 · 原则 8「commit message 默认中文」
```jsonc
{ "rule_id": "an:PRINCIPLE-8",
  "type": "tool_call",
  "trigger": { "tool": "Bash", "pattern": "git\\s+commit" },
  "compliance": { "pattern": "-m\\s+[\"'][^\"']*[\\u4e00-\\u9fff]" },
  "violation": { "pattern": "-m\\s+[\"'][A-Za-z0-9 _.:;'\"()/-]+[\"']\\s*$" },
  "calibration": { "positive_samples": ["git commit -m 'fix: English only msg'"],
                   "negative_samples": ["git commit -m 'fix(核心): 修复 x'"],
                   "hit_cap": 20 } }
```
校准集来源：**git log 历史即为天然校准集**（过去数十条 commit，中英混合）——先离线跑锚点对全部历史 commit，人工核 mismatch，再上线。
**已知弱点（诚实）**：多 `-m` 段、代码术语混排（`fix(core): 修复 parser`）会造成 uncertain——预期 uncertain 率不低，试点先测。

### 试点 2 · 原则 9「破坏性操作必须指定目标」
```jsonc
{ "rule_id": "an:PRINCIPLE-9",
  "type": "sequence",
  "trigger": { "tool": "Bash", "pattern": "\\brm\\s+-[rf]|pkill|docker\\s+(rm|stop)" },
  "compliance": { "pattern": "前 5 iter 内存在对同一目标的 ls/echo/查询记录，或 rm 目标为带引号字面量" },
  "violation": { "pattern": "\\$\\(|未加引号通配|\\s\\*\\s*$" },
  "calibration": { "positive_samples": ["pkill -f agent"], "negative_samples": ["pkill -x zcode"], "hit_cap": 10 } }
```
**已知弱点**：「前 5 iter 有 ls」的序列匹配对 iter 跨度敏感；试点先用**保守版**（只抓 `$(...)` 与未引号 `*` 两个确定违规形态），序列版放 M3。

### 试点 3 · R-004「删兼容层必跑审计」（审计命令是安全网）
```jsonc
{ "rule_id": "an:R-004",
  "type": "sequence",
  "trigger": { "tool": "Bash", "pattern": "git\\s+rm|\\bDelete\\b.*兼容层|check_compat" },
  "compliance": { "pattern": "同会话后续存在 batch_gate / check_ 脚本执行" },
  "violation": null,                         // 无法确定性判定违规 → 只有 complied/uncertain
  "calibration": { "positive_samples": [], "negative_samples": [], "hit_cap": 5 } }
```
**已知弱点**：「同会话后续」的窗口定义（本会话？下个 iter？）试点时定；违规侧无法机检 ⇒ 该锚点只产 complied/uncertain，统计口径要注明。

## 6. 与其它层的关系

- **与 script 通道**：正交互补——R-002 例：script 查落盘代码，regex 查会话中 Edit 前是否先声明 ENV_TABLE（行为过程）；两层都记，不互替；
- **与 judge 通道**：regex 锚点覆盖不到的散文原则（Think Before Coding 等）留给 judge（待 A4 校准）；regex 的 uncertain 样本是 judge 的**天然输入**（分层观测：regex 先筛，模糊上交）；
- **与触发场景库**：锚点的 calibration positive/negative 样本与场景库同源——场景库给「规则该触发的情境」，锚点给「触发后的判定模式」，M3 合流。

## 7. 诚实边界

1. regex 锚点只覆盖**表面行为**——语义等价的绕过（换工具、换措辞）不可见；查全率上限由工具面决定，试点须报告**覆盖比例**（哪些规则有锚、哪些没有）；
2. 三条试点的 pattern 均为**待校准草案**——校准（§4）跑完并核对 mismatch 前，任何数字不得引用；
3. uncertain 预期不低（试点 1 的中英混排）——这本身是量具发现：uncertain 率过高的锚点应降级为「human 抽查提示器」而非自动记账；
4. 本细则不改变门禁失败语义（可行性 §8 红线）：regex 通道只记账，不阻断。
