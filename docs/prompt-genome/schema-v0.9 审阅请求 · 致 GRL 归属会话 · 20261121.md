## 0. 我们做了什么（一句话）

以 GRL 的字段语义为**基底**（全部实测结论原样吸收），把 Registry（治理/验证字段）与 Locus Table（坐标系）合并成**一个对象模型 + 两个域扩展包 + 观测零内联**的统一 schema（v0.9，186 行，含三实例 JSON）。

## 1. 明确不动的东西（先说安全边界）

- GRL 的 18 条机检判据（grl_check.py）、5526 条款实测数据、modality 量表 / negation 三态 / allele_key L2 分辨率——**全部原样吸收为 schema 语义，一字未改**；
- 本规格**只加字段**（protobuf 式）：allele_key / source_span / provenance 四元组扩展 / S 域扩展包；
- 唯一改名：`locus` → `locus_id`（对齐位点表主键），需一次性重编码，成本见 Q4。

## 2. 七个待确认问题（逐题请作答：同意 / 修改（怎么改） / 否决（为什么））

### Q1 · W 域 `tier` 的语义（规格自认的新解释，最需要对齐）
规格把 W 域对象的 `tier: 0` 解释为「**厂商自冻结强度**」——即该厂商对这条条款的自我约束等级，而非 AgentNodes 的提案权限。这是规格**新引入**的解释，未与你们对齐。
**请确认**：GRL 的 tier 在 W 域语料里实际编码的是什么？（若你们的 tier 在 W 域只是从条款形态推断的标注，建议改名为 `tier_w` 或降级为 provenance 附属字段。）

### Q2 · modality 六值量表扩展到 S 域 + 强度守恒机检
registry 旧三值（MUST/禁止/SHOULD）映射为 must/must_not/should。**请确认**：强度守恒检查（§3.4，12711 次 0 违规）是否应扩展到 S 域对象——S 域规则是**中文**，你们的守恒机制按英文风格表实现，跨语言是否成立？

### Q3 · allele_key 在 S 域（中文语料）的分辨率
L2 分辨率（scope+modality+negation+verb）实测基于全英文语料。S 域规则中文书写，`scope.key` 归一键 + `verb` 英文化后分辨率是否退化？
**我们的假设**：scope.key 与 verb 用受控英文词表（编码器翻译），中文原文保留在 object.raw / definition——**请确认这个跨语言策略是否与你们的作用域归一（§3.3）兼容**。

### Q4 · `locus` → `locus_id` 改名的重编码成本
5526 对象一次性重写 + 批清单记版本。**请确认**：① 你们是否接受此改名（或位点表主键改叫 `locus` 保持 GRL 不动？——我们倾向改 GRL，因 U4 已把位点表定为独立工件）② 重编码由谁执行（你们工具链 vs 我们 M1 解析器）。

### Q5 · 四种引用形态的解析源变更
`#D01`（位点引用）与 `#D01~must`（等位引用）的解析源在规格里改为**位点表**（原来解析自编码对象集合）。**请确认**：断言求值（⊇/⊥/≡，C9 互补性）在解析源变更后行为是否不变——特别是「位点下无对象」时断言的空集语义。

### Q6 · module/override 在 S 域的启用
S 域暂无模块需求，规格只留了 `module{}` 接口位。**请确认**：override 的 Tier 0 编译器硬拒（你们 §2.3）在 S 域是否直接复用——AgentNodes 侧对应物是 `TIER0_COMPONENTS` 构造时拒绝（genome_proposals.py），语义一致但实现层不同。

### Q7 · IDSPACE 前缀 `cl4r:` 的授权注意
U2（未拍板）拟用前缀注册表区分两域 id：`an:`（自仓）/ `cl4r:`（语料）。语料含 AGPL 覆盖的厂商专有提示词（CL4R1T4S 评估 F4 的法律瑕疵）——**请确认**：以 `cl4r:` 前缀引用这些对象（只引用原文指针 + sha256，不复制内容）是否与你们对语料授权问题的处理一致；是否需要一个更中性的前缀（如 `wc:` wild-corpus）。
