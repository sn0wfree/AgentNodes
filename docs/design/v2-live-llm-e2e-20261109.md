# V2 · 真实 LLM 端到端验证（2026-11-09）

> **触发**：用户要求「第一步完成的标志就是可以变成一个通用 agent 正常使用；
> 有完整的基础功能，可以 chat 可以执行代码 可以进行 coding」。
> E1–E5 / parity / skeleton equivalence 全是 mock LLM——真实模型下没有证据。
>
> **结论：5 个场景全过（84s），过程中抓到 2 个真实的框架 bug。**

## §0 模型与配置

用户提供：宿主已有 `~/.agentnodes/llm.json` + `~/.agentnodes/.env`（MINIMAX_API_KEY）。
按要求切到 **`MiniMax-M3.1-Flash`**，参数从官方文档核对后写入：

| 参数 | 值 | 依据 |
|---|---|---|
| `model` | `MiniMax-M3.1-Flash` | 官方 `/v1/models` 确认存在（created 时间最新）|
| `model_context_tokens` | 1,000,000 | 官方文本模型表 |
| `model_max_output_tokens` | 128,000 | M3 系列同源（官方未单列 M3.1-Flash 输出上限）|
| `enable_thinking` | **True（强制）** | **官方：传 `thinking:disabled` → 400 `requires adaptive thinking`** |
| `temperature` / `top_p` | **不设** | 官方：不支持指定（固定 1 / 0.95）|
| `timeout` | 300s | 1M 上下文 + thinking，长任务耗时长 |
| 价格 | 输入 ¥1.00 / 输出 ¥4.00 / 缓存 ¥0.10（每百万 tokens）| 官方定价页 |

**踩坑**：`M3.1-Flash` 不在内置 catalog（只有 `MiniMax-M3`），走 `fallback`
（200k/4096）。必须显式配 `model_context_tokens` / `model_max_output_tokens`，
否则上下文被低估 5 倍、输出被限制到 4k。

**官方关键约束**：`max_tokens` **包含思考 token**——设太小会导致
`finish_reason=length` 且 `content` 为空。

## §2 抓到的 Bug #1：skeleton 路径 assistant 消息丢失（**严重**）

### 现象

MiniMax 返回 400：
```
invalid params, tool result's tool id(call_01a1bf...) not found (2013)
```

### 根因

`_make_strategy_ctx` 做 `messages=list(messages)`（**浅拷贝**）：

1. `LoopReasoner` 用副本创建 `llm_ctx`
2. `DefaultLLMCallStep` 往**副本** append assistant 消息
3. `LoopReasoner` 只回写 `ctx.response`，**没回写 `ctx.messages`**
4. `LoopActor` 往**原列表** append tool 结果

→ 发出的消息序列是 `[system, user, tool]`，**缺少带 `tool_calls` 的
assistant 轮次**。任何多轮工具调用都会失败。

### 为什么之前没发现

多数 provider 不校验 `tool_call_id` 的存在性（宽松接受），所以 mock 测试和
其它 provider 都没暴露。**MiniMax 的严格校验把它逼出来了。**

### 修复

`LoopReasoner` 回写 `ctx.messages = llm_ctx.messages`（1 行 + 注释）。

## §3 抓到的 Bug #2：直接构造 AgentLoop 时权限闸不接线（**安全**）

### 现象

真实模型执行 `sudo echo LIVE_SUDO_TEST` → **`status: ok`，实际执行了**。
而同一个场景走 `build_chat_agent_loop` 是被拦住的。

### 根因

`AgentLoop.__init__` **完全没有** `_permission_evaluator` 的赋值——
它只被 `chat_loop.build_chat_agent_loop` 用 `setattr` 挂上去。

所以：
- ✅ `build_chat_agent_loop`（生产 web chat）→ 有权限闸
- ❌ **直接 `AgentLoop(config, registry, ...)`** → 无权限闸，工具裸执行
  （evals / scheduled_research / 测试 / 脚本全走这条）

### 修复

`AgentLoop.__init__` 默认接线，与 `chat_loop` 规则一致：
- spec 显式给了 → 用它
- 否则按 `AGENTNODES_PERMISSION_MODE` → 无则 L2（shell 自动，hard_deny 兜底）
- 异常不阻断构造（`logger.debug` 后继续）

## §4 测试环境踩的坑（不是代码问题）

### 4.1 conftest 的 home 沙箱让 `LLMConfig.load()` 读到空配置

`_home_sandbox.apply()` 把 `USERPROFILE` 指向 `tests/_user_home_sandbox/`。
而 `quantnodes_bridge.CONFIG_PATH` 是 **import 时求值**的模块级常量——
已凝固成沙箱路径。所以 `LLMConfig.load()` 拿不到宿主配置，回落默认值
（`provider=auto` / `gpt-4o-mini` / `api.openai.com`），请求超时。

**修法**：V2 的 `_load_real_llm_config()` **不经 load()**，直接从
宿主真实路径读 `llm.json` + `.env`，手工构造 `LLMConfig`。

### 4.2 `pytest.mark.live_llm` 豁免

`_purge_llm_env` 是 autouse fixture，每测前清空所有 `*_API_KEY`。
新增 `live_llm` marker：标了它的测试跳过清除（它们已有双重 opt-in）。

### 4.3 一个残留的诊断文件导致 pytest 崩溃

我临时写的 `tests/test_diag_live_network.py` 在模块级重包装 `sys.stdout`，
pytest 退出清理时报 `ValueError: I/O operation on closed file`，
现象是 `no tests ran` + `INTERNALERROR`。删掉即恢复。

**教训**：临时诊断脚本**不要放进 `tests/`**——会被 pytest 收集。

## §5 结论

**第一步的核心能力在真实模型下全部成立**：chat 多轮、代码执行、coding
（读→改→验证）、权限边界、预算停止。

且 V2 的价值不只是"证明能用"——它抓到了两个 mock 测试**结构上不可能**
发现的 bug：
- Bug #1 依赖 provider 的严格校验（mock 不校验）
- Bug #2 依赖「直接构造 AgentLoop」这条路径（生产 chat 不走）
