# W1-3 审计报告 — L3→L2 上行边逐条分类（2026-11-03）

审计类 · 不改代码。口径 = ADR-000 物理口径（每语句计 1）。
方法与证据：`tmp/dump_gate_l3l2.py`（用门禁自身 resolver dump）、`tmp/w13_scope.py`（AST 作用域判定）。

## 0. 关键结论（推翻预设）

**46 条里 44 条是函数体内的 lazy import，只有 2 条是模块级静态依赖。**

这意味着「L3 严重耦合 L2、需要 CapabilityRegistry 端口化 46 条」的叙事**不成立**。
`builtin_tools` 里的 `from ....core.db import ...` 写在工具函数体内，是 Python 规避
循环导入的标准用法（模块级写会形成 import cycle），不是分层违规的实质耦合。

## 2. 对 G2b（CapabilityRegistry）的判断输入

- **B 类仅 5 条、且集中在 2 个数据工具函数** → 端口化收益小。
- **A 类 6 条在 scheduled_research 与 swarm 编译器** → 这是「执行面/调度面知道研究域」，
  应通过**事件流 + Directive**（已存在的机制）解耦，不是 Registry。
- **模块级 2 条** → 可改为工具注册回调（`ToolRegistry` 的既有模式）。

## 3. 建议（供 W2-3 ADR-003 决策）

1. **不建 CapabilityRegistry**（B 类 5 条不值得一个端口层；重开条件：B 类 > 15 条
   或出现第 3 个消费方）。
2. A 类 6 条单独立项「scheduled_research / swarm 编译器去研究域化」——收敛到
   `study.directive` 事件 + Gateway 提交，属 B3 执行批。
3. 模块级 2 条改为注册回调（小改，可并入 G2a）。
4. C 类 35 条**判定为合规**（lazy import 惯用法），但门禁仍计数——建议门禁对
   「函数体内 import」单独归类为 `L3~L2(lazy)` 不计入棘轮，或改为可接受的
   已知基线（当前 46 即含它们）。此项属 W4-1 门禁规则工作项。
