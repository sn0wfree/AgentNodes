## 2. 判定门（实施计划 3.2 要求：阈值 + 依据）

**提议阈值：D 类 > 30% ⇒ 哑适配器叙事失真。**

实测 D 类 = 62%（88/141）——**远超阈值，叙事失真成立**。

依据：`api/app.py` 与架构图的定义是「哑适配器：只构造 WorkRequest + 订阅事件流」。
但实测 `api/routers/goal.py` 直接调 `GoalStore` CRUD、`workflow.py` 直接构造
`GoalWorkflowRunner`、`cli/__init__.py` 直接注册 7 个研究域命令——
**这些是业务逻辑，不是「构造请求」**。

**但需诚实标注一个限定**：`GoalStore` 一类「账本类」的构造在 L1 是**可辩护的**
（路由需要读账本做展示；账本属数据访问而非编排决策）。真正越界的是
`GoalWorkflowRunner` / `CheckpointStore` / `cmd_goal_*` / `build_autoresearch_workflow_config`
——这些是**编排决策**，应经 Gateway 提交。

保守估计：**真正越界（编排决策类）约 20 条，占 14%**；账本直读约 68 条占 48%；
类型/常量约 45 条 32%。

## 3. 对 W2-2（ADR-002 哑适配器策略）的建议输入

1. **不追求「零直连」**：账本直读（48%）是合理设计，强行收敛到 WorkRequest 会把
   简单读查询变成异步事件往返，净负收益。
2. **收敛目标锁定「编排决策类」20 条**：`GoalWorkflowRunner`、`CheckpointStore`、
   `cmd_goal_*`、`build_autoresearch_workflow_config`、`load_goal_workflow` 应经
   Gateway 提交（多数已在 R3/E2 迁移范围）。
3. **门禁规则建议**：L1→L2 计数区分「账本/类型读取」与「编排驱动」两类；
   后者单独设棘轮基线（20 条 → 0），前者允许。
